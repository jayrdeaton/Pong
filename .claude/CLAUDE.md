# Pong

A digital Pong game (Expo/React Native, Skia-rendered). Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem - depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/splash-gate`, `@rific/toaster`, `@rific/updater`, `@tastic/core`, `@tastic/hud`, `@tastic/physics`, `@tastic/profile`, `@tastic/split-screen`.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code - don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest (14 suites, 204 tests)
npm run test:watch     # Jest --watchAll
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) - `verify` doesn't include a build step.

`build`/`update` are single bare scripts (`rific-updater-build`/`rific-updater-update`) delegating to `@rific/updater`'s own CLI - there's no per-profile `build:development`/`update:production`-style script in this app's `package.json` at all, and no `npm run verify && ` prefix anywhere. The `verify` gate runs inside the CLI itself, as its first step, shared by both bins. See `@rific/updater`'s own README (`../Expo-Updater/README.md`, "Verify-gating lives in the CLI, not in `package.json`") for the full mechanism - that doc explicitly flags the old per-script-prefix pattern as one it replaced, which is what an earlier version of this paragraph was still describing.

## Two-player achievement toasts + shared-package extraction (2026-09-17)

A fleet-wide audit found one real, live user-facing bug: `showAchievementToast` (`@rific/toaster`) is a single, screen-fixed toast with no rotation of its own, so in genuine two-player pass-and-play (`aiPlayer === null`) a player seated opposite - rotated 180° from whoever is holding the device in this app's faceToFace hold - couldn't read an achievement toast that was actually theirs. Fixed in `src/app/game.tsx`'s gameOver effect: the `aiPlayer === null` branch now broadcasts unlocks (device-scope ones included, attributed to both seats since both are human here) into a new `seatUnlocks` state instead of firing the toast, rendered as a per-seat row list inside the existing two-player game-over overlay - which already carries the board's own `rotationStyle` - each row tagged with the earning seat's own `ProfileChip` (falling back to a plain color-circle avatar for a guest seat, mirroring `winnerProfile`'s own P1/P2 fallback). `aiPlayer !== null` (vsCpu, exactly one human seat, never a genuine two-seat faceToFace hold) is unaffected and still uses the shared toast - same pattern LightCycles' own `game.tsx` already applies via its `profileUnlockToast`, for the identical reason.

Five duplicated pieces of code across this app and 4 siblings (AirHockey, BoxHockey, LightCycles, Snake) were extracted into shared packages in the same pass, and this app migrated onto them:

- `RotationAwareStatusBar` moved from a local ~10-line function in `_layout.tsx` into `@tastic/core` - the same extraction AirHockey/BoxHockey/LightCycles had already made, so this app is catching up to an established pattern rather than setting one. The shared component takes a `locked` prop; `_layout.tsx`'s own `AppRotationAwareStatusBar` wrapper now reads `settings.lockOrientation` from `useGameSettings()` and threads it through, in place of the old version's direct `useOrientationState()`/`getViewRotation()` calls. (Superseded 2026-10-07: no `locked` prop anymore, see "Lock Orientation is app-wide" below.)
- `PlayerSetupPanel` moved from `src/components/PlayerSetupPanel.tsx` (deleted) into `@tastic/hud`, generalizing its old `controlScheme`/`onControlSchemeChange`/`controlSchemeOptions`/`otherControlScheme` props into one generic `secondPicker`/`secondPickerId` slot. `src/app/loadout.tsx` renders `@tastic/hud`'s own pre-existing `ControlSchemePicker` (also used by AirHockey's and Snake's own panels - not new, and not Pong-specific) into that slot for both seats.
- The staggered-letter "PONG" wordmark animation (the old local `AnimatedLetter`/`Word` helpers) moved out of `src/components/HeroTitle.tsx` into `@tastic/hud`'s new `StaggeredWord` component + `getStaggeredWordDuration` helper, which generalizes the identical 45ms-stagger/320ms-per-letter/back-ease animation five apps (AirHockey, BoxHockey, Pong, LightCycles, Snake) had each hand-rolled separately.
- The Redux-backed `FeedbackBridge` in `src/components/Providers.tsx` now builds its `FeedbackPressProvider` props via `@rific/feedback-press`'s new `useFeedbackBridgeProps` hook instead of passing `initialValue`/`onChange`/`soundInitialValue`/`onSoundChange`/`sound` individually.
- `src/utils/achievementEngine.ts` shrank from two hand-written wrappers around `evaluateUnlockedIds`/`unlockedKey` to one `createAchievementBindings(ACHIEVEMENT_CATALOG, getProfileStatsView)` call from `@tastic/achievements`, destructured to the same three export names - no call site elsewhere needs to change its import path.
- `src/redux/profileSelectionSlice.ts` shrank from a hand-rolled `createSlice` (identical to 4 sibling apps' own copies) to `createProfileSelectionSlice<Player>('pong', defaultProfileSelectionState)` from `@tastic/profile` - the `'pong'` argument namespaces the slice, the same generic factory call each sibling now makes with its own app name.

Two more real, unrelated fixes landed in the same working tree, touching files this pass already had open:

- **Seat color overrides now persist.** `redux/seatColorsSlice.ts` gained a persisted `profileOverride: Record<Player, string | null>` field - a profile-selected seat's manual recolor/clash-swap used to live only in the transient live theme color, so merely leaving `/loadout` and returning (not even a real profile change) silently reverted it back to the profile's saved color. `loadout.tsx`'s recolor handlers now dispatch `setProfileOverride` for a profile-selected seat instead of touching `lastGuestColor`/`lastCpuColor`, the focus-effect reapply resolves `override[seat] ?? profile.color` instead of always trusting the profile's saved color, and both `onProfileSelect` handlers clear that seat's override back to `null` the moment its selection actually changes. Landed 2026-09-16, per Jay's original ask that profile colors and overrides survive relaunch. **Superseded 2026-09-18:** this file is now a thin binding over `@tastic/profile`'s new `createSeatColorsSlice<Player>('pong', defaultSeatColorsState)` factory rather than a hand-rolled reducer - see that package's own CLAUDE.md for the factory's full history (including its own `REHYDRATE` fix, which this app inherits for free).
- **Stored settings blobs now merge onto defaults before validating.** `@tastic/core`'s `createGameSettingsProvider` - which `useGameSettings.tsx` calls straight into, passing this app's own `storageKey`/`defaultSettings`/`isValidSettings` - used to run `isValidSettings` directly on whatever JSON was parsed, so a blob written before some `GameSettings` field existed (missing that one field) failed the all-fields check and silently discarded every other still-valid preference in it too - not just the new field. It now spreads `{ ...defaultSettings, ...parsed }` before validating, so an old blob only ever loses the field(s) it genuinely predates.

`_layout.tsx` also picked up one small, independent tweak: `<Toaster historyButton={null} clearButton={null} limit={3} />` explicitly turns off the history/clear button row (this app has no history-modal use case for them to open) and pins `limit` to `@rific/toaster`'s own current default rather than relying on it implicitly.

**A live browser check of AirHockey's `/loadout` screen (its migration this same round is byte-for-byte the same shape as this app's own) turned up a real bug in `@rific/core`, upstream of this app's own `Theme.tsx`/`GameSettingsProvider`/`OrientationProvider`.** `createSettingsContext`'s `set()` called the consumer's `onChange` *inside* the `useState` updater passed to `setSettings` - a `useState` updater must be pure, since React can invoke it outside the originating `set()` call (e.g. replaying a queued update while resolving a later render of the very same Provider), and when that happened, `onChange` (which `Theme.tsx` wires straight to `dispatch(themeActions.initialize(...))`) fired synchronously mid-render of an unrelated component - a genuine "Cannot update a component while rendering a different component" React warning. This factory backs `@rific/auto-paper`'s `Theme`, `@rific/feedback-press`'s haptic/sound settings, and `@rific/scroll-view`'s settings context alike. The same audit found the identical shape independently duplicated, not through this factory, twice more inside `@tastic/core`: `createGameSettingsProvider`'s `setSettings` called `AsyncStorage.setItem` from inside its own updater, and `OrientationProvider`'s `set` called the consumer's `onLockChange` the same way - both used by this app. All three were fixed the same way: the side effect moved into a `useEffect` keyed on the settled state, skipping the mount-time run so the contract (onChange/persistence only fires for a real `set()` call, never for `initialValue`/`defaultSettings` seeding) is unchanged. Now on `@rific/core@0.1.2` and `@tastic/core@0.5.1` (both patch bumps, no API change) - this app's own `npm run verify` (177/177 tests) stayed green through the bump.

**Same pass also found and fixed a real gap in `@infinitetoken/jest-config`'s `knownSubpathMocks`:** it stubbed `@rific/feedback-press/audio`'s `useAudioPool` but not `useGatedAudioPool` - a real risk for this app specifically, since `hooks/useGameSound.ts` re-exports `useGatedAudioPool` directly, and any future test rendering a component that calls it would have hit real `expo-audio`/native audio APIs during a Jest run instead of the intended inert stub. Fixed by adding the same inert-hook stub for it. Now on `@infinitetoken/jest-config@0.3.1`.

**`@tastic/hud@0.9.0` closed the `PlayerSetupPanel` CPU-difficulty alignment gap this app's own earlier migration agent found blocked (no override prop existed at all for the panel's internal `LabeledDropdown`) - `loadout.tsx`'s `p2Panel` now wires the new `cpuDifficultyAlignOverride` prop via `useZoneClampedAlign(p2Host.openId === getCpuDifficultyPopoverId('p2'), LABELED_DROPDOWN_POPOVER_WIDTH, getLabeledDropdownContentHeight(AI_DIFFICULTY_OPTIONS.length))`.** Confirmed, from the actual render tree (not assumption), that this is a documented no-op for this app: the CPU-difficulty picker only ever renders for a non-human seat 2, which only exists in `vsCpu` mode, and `vsCpu` always takes the plain stacked `View` branch of the `gameMode === 'twoPlayer' ? <DualZoneLayout .../> : ...` split - `DualZoneLayout` (the only `@tastic/split-screen` zone-producer this screen ever mounts) wraps exclusively two-player's own panels. So `useZoneBounds()` is null there and `useZoneClampedAlign` falls straight back to `useAutoAlign`'s own plain screen-edge placement, same conclusion LightCycles' own `lobby.tsx` already documented for its identical seat before this prop existed. Wired in anyway, for parity with every other zone-aware popover in the fleet and so it starts clamping for free if `vsCpu` is ever nested inside a zone later. `npm run verify` (177/177 tests) stayed green.

## Fleet package extraction round 2 (2026-09-18)

Eight more pieces of duplicated code across this app and its siblings (Snake, AirHockey, BoxHockey, LightCycles) were extracted into shared packages, and this app migrated onto all of them. Versions landed: `@rific/core@0.1.4`, `@tastic/achievements@0.1.2`, `@tastic/hud@0.11.0`, `@tastic/profile@0.6.0`, `@tastic/core@0.7.0`, `@rific/auto-paper@0.11.1` (all yalc-linked, per `yalc.lock`).

- **`safeBack` (`src/utils/navigation.ts`)** now binds to `@rific/core`'s shared implementation instead of a locally hand-rolled `router.canGoBack() ? router.back() : router.replace('/')`. The file shrank to a 6-line shim: `configureNavigation({ router })` at module load (injecting `expo-router`'s real `router` object into `@rific/core`, which never imports `expo-router` itself - it only mirrors the 3 methods it calls as a local `SafeBackRouter` type, keeping the package's zero-hard-dependency posture intact) followed by `export { safeBack }`. Every existing call site (`safeBack()` in `game.tsx`/`achievements.tsx`, `onBack={safeBack}` in `profiles.tsx`) needed zero edits - `safeBack` kept its exact zero-argument signature specifically so it still works as a bare callback reference, not just a direct call.

- **Achievement seat translation (`src/hooks/useGameStats.tsx`, `src/app/game.tsx`)** - the profile-id-keyed → seat-keyed translation loop in `recordMatchOutcome` is now one call, `mapUnlocksBySeat([1, 2] as Player[], context.profileIds, result.profiles)`, replacing a hand-rolled `for (const seat of [1,2])` loop. `game.tsx`'s two-player achievement-toast branch now calls `broadcastDeviceUnlocks([1, 2] as Player[], result.profiles, result.device)` in place of the old imperative `broadcast[1] = [...]; broadcast[2] = [...]` mutation, both from `@tastic/achievements`. **Not adopted:** `recordSoloOutcome` (Pong's second, single-seat call site - solo mode's own recorder) still hand-rolls its own `if (profileId) { ... profiles[1] = unlocked }` translation rather than wrapping the bare profile id into `mapUnlocksBySeat([1], { 1: profileId }, ...)` - a deliberate non-adoption, since bending a single `string | undefined` into a seat-keyed map for one 4-line block wasn't judged worth the indirection.

- **Quit confirmation (`src/app/game.tsx`)** now uses `@tastic/hud`'s `useQuitConfirmation`, replacing the local `confirmBackVisible` state + `onBackPress` callback + `ConfirmDialog` visible/onCancel wiring. The hook's real signature takes a **lazy `hasProgress: () => boolean` getter, not a plain boolean** - a correction made after the hook's first version, which took a plain boolean and broke exactly this app's own shape: `paused` (`settingsOpen || confirmVisible`) has to be computed and handed to `useGameState()` *before* that call returns the `lives`/`bricks`/`scores` state `hasProgress` needs to read, so a plain-boolean argument is a real circular dependency (`confirmVisible → paused → useGameState → state → hasProgress → confirmVisible`). Pong is one of the three apps (with AirHockey and BoxHockey) whose shape forced this correction. No local workaround was needed once the hook itself was fixed - the call site just passes an inline closure directly: `useQuitConfirmation(() => (isSolo ? lives < SOLO_LIVES || bricks.some((b) => b.destroyed) : scores[0] > 0 || scores[1] > 0), safeBack)` (`game.tsx`, ~line 160), and the hook's own `useRef`-mirrored getter (refreshed every render via a dependency-less effect) guarantees `requestBack` always reads the latest `lives`/`bricks`/`scores` at call time rather than a stale closure. `ConfirmDialog`'s own JSX (title, per-mode `message`, icon, labels, `rotation`) stays authored at the call site as before - the hook only owns `confirmVisible`/`requestBack`/`cancelBack`.

- **Achievements scaffolding (`src/app/achievements.tsx`)** now uses `@tastic/achievements`' `getAchievementCatalogRows` to compute each catalog row (scope, unlockedAt, progress, tierColor, deviceMarker) in place of the old local `ACHIEVEMENT_CATALOG.map(...)` loop, and `@tastic/hud`'s new `AchievementCatalogSection`/`ActivityStatSection` components to render the "ALL ACHIEVEMENTS" list and the Days-Played/Streak block, replacing the local `MS_PER_DAY`/`startOfDay`/`unlockedLabel` formatter and the `<StatSection label='ACTIVITY'>` block outright. `AchievementCatalogSection` (`@tastic/hud@0.11.0`) imports its `AchievementCatalogRow` type as a real, type-only peer dependency straight from `@tastic/achievements` - confirmed from the installed package's own source, which now carries a comment noting the type is "no longer duplicated locally now that package has actually published the export" (an earlier draft of this component briefly held its own local copy of the type before `@tastic/achievements` shipped it - this app is on the corrected, real-import state). Pong's own app-specific `OVERALL`/`POINTS`/`VS CPU`/`TWO PLAYER (LOCAL)`/`BALL SPEED (W-L)`/`PLAYER RANKINGS` `StatSection`s and its local `ProfileRankingRow` component are untouched - none of that was in scope, and this app's local `MONO_FONT` import (`@/constants/fonts`) is still genuinely in use elsewhere in the file (the ranking row, the loading-state text), unlike the AirHockey/BoxHockey case where this section was its only consumer.

Pong's route now just wires `profiles`, `defaultColor={defaultColors[0].value}` (from `@rific/auto-paper`) - its own `CreateProfileInput` is exactly `@tastic/profile`'s base `{name,color,tag}` shape, unlike BoxHockey/LightCycles, which compose an extra required field onto the patch inside their own `onCreate` - plus the three CRUD callbacks (`onDelete` still calls `removeProfileStats(id)` alongside `deleteProfile(id)`, unchanged) and `onBack={safeBack}`.

The `false` passed for `gestureEnabled` carries no rationale comment here (Pong never documented why it disables the native swipe-back, unlike Snake's/LightCycles' own prose about `TouchInputLayer`'s Pan gestures) - the hook deliberately keeps `gestureEnabled` a caller-supplied parameter rather than folding it into the corner-flash fix, specifically so an undocumented-but-load-bearing value like this one carries forward unchanged instead of being silently "cleaned up" during the migration.

## How-to-play guide (2026-09-24)

A first-run, replayable "how to play" flow, built on `@tastic/hud/guide` (a light-peer subpath of `@tastic/hud`; see that package's own CLAUDE.md, "The guide subpath"). Same wiring as the LightCycles pilot. **Do not call any of this "onboarding"**: LightCycles and Snake already use that word for their 3-2-1-GO countdown, so the how-to-play code is `guide` everywhere.

- **Content:** `src/constants/guideSteps.tsx`, `getGuideSteps({ touch, controls, scoreToWin })`, three cards, pure and hook-free: Move Your Paddle / First to 5 Points Wins / Two Players, One Phone. On desktop web the last one is the fleet's shared desktop two-player card: "Two Players, One Keyboard" when both seats are on key schemes, "Two Players, One Computer" whenever either seat is on the mouse (the default: P1 `'mouse'`, P2 `'wasd'`). `controls` is the live `settings.controlScheme` and `scoreToWin` the live `settings.scoreToWin` (3/5/7/10), so a replay after the loadout names the real setup, not the defaults. What it teaches (none of it is printed in-game): the paddle lines up with your finger or the pointer (absolute position, so you never have to touch the paddle itself), you score by getting the ball past the other paddle, first to `scoreToWin` wins, and in two-player each player drags in their own half.
- **Pong-specific truth calls** (the guide shows on Home before any mode is picked, so every reader sees every card):
  - The steering card never says "your half" or "anywhere": One Player's touch zone is the whole screen, two-player's is a half (`TouchInputLayer.tsx`). "Your own half" lives only on the two-player card.

## Settings and Lock Orientation (2026-10-07)

**Settings live in Redux**, like every other persisted value: `src/redux/settingsSlice.ts` (`DEFAULT_SETTINGS` plus `@rific/core`'s `createSettingsSlice('settings', { initializeMode: 'merge' })`), read and written only through `useSettings()` (`src/hooks/useSettings.ts`, returning `{ settings, setSettings(patch) }`). There is no validation and no migration: the factory's REHYDRATE handling fills any field added since a player's settings were saved from the defaults. Settings saved by older builds under the old AsyncStorage settings key were deliberately abandoned (Jay, 2026-10-07). `PersistGate` (in `Providers.tsx`) holds rendering until the store has rehydrated, so there is no settings splash gate; `_layout.tsx`'s `GatedApp` waits only on profiles. This replaced `@tastic/core`'s `createGameSettingsProvider`/`GameSettingsProvider`/`useGameSettings` and the per-game `isValidSettings`.

- **Per-round state** lives in `src/redux/liveplaySlice.ts`, blacklisted from persistence in `store.ts`: `activeRoundSettings` (the snapshot the loadout commits when every human player readies up, so a mid-match settings change only affects the next match) and `activelyPlaying` (written by `/game`, read by `Providers.tsx`'s `EdgeGuardBridge`, the only `useEdgeGestureGuard` call).
- **Lock Orientation** is app-wide via `@tastic/core`'s `OrientationProvider` `freezeWhileLocked`, wired in `_layout.tsx`'s `OrientationBridge`. While locked, the ONE shared orientation reading freezes for every consumer: every screen's `useOrientationState()`/`useRotation()`/`FakeLandscapeView`, the in-game board (touch mapping included), hud dialogs, `GuideHost` and `RotationAwareStatusBar`, including anything that mounts after the lock. Never hand the setting to a call site (`useOrientationState(x)`, `useRotation(x)`, `<FakeLandscapeView locked>`, `<RotationAwareStatusBar locked>`): a per-call-site lock freezes on the pre-sensor portrait default at mount, which is the relaunch bug this replaced.
- **`lockedRotation`** (optional `ViewRotation` on `Settings`, absent from `DEFAULT_SETTINGS`): the locked angle, recorded by `onLockChange` on lock and cleared on unlock, never set by UI. Handed back through `lockInitialValue`, it makes a relaunch open in the locked orientation from the first frame. The Settings dialog toggle only writes `lockOrientation`; the provider adopts the changed `lockInitialValue` after mount (`@rific/core` 0.3.0+) and reports the angle back, so it applies immediately, mid-match included.
- **Byte-identical across AirHockey, BoxHockey, LightCycles and Pong:** `_layout.tsx`, `liveplaySlice.ts`, `achievementsSlice.ts`, `useSettings.ts`, `settingsSlice.test.ts`, `Providers.tsx`'s `EdgeGuardBridge`, everything in `settingsSlice.ts` except `DEFAULT_SETTINGS`, and this section. Change them in all four or none, so any game can template the next.
- **Stats and achievements live in Redux too** (2026-10-07): `src/redux/achievementsSlice.ts` (`@tastic/achievements`' `createAchievementsSlice`, mounted as `achievements`; byte-identical across AirHockey/BoxHockey/LightCycles/Pong/Snake), read and written only through `hooks/useGameStats.tsx`'s `GameStatsProvider` (`useAchievements` with `select`/`actions`). Needs `@tastic/achievements` 0.3.0+. Old AsyncStorage stats and achievements were deliberately not imported: players start fresh (Jay). Nothing loads asynchronously anymore, so the achievements screen has no loading guard and `useGameStats()` has no `loaded`.
- Needs `@tastic/core` 0.11.0+. Lock Orientation is native only: web derives its reading from the window shape and is never frozen.
- **Pong only:** `/game` keeps one per-screen lock on top, `useOrientationState(tiltControlActive)`, so tilt steering can't rotate the board mid-rally even with the setting off.

## Background pause, profile prune, control scheme swaps (2026-10-08)

- **Background pause:** `game.tsx` calls `@tastic/core`'s `useBackgroundPause`. Any AppState change away from `'active'` mid-match (home, app switch, a call, iOS `'inactive'` for Control Center; a hidden tab on web) latches `backgroundPaused`, which is ORed into `paused`, so the game loop, serve pause, AI, all three input layers and Edge Guard stop exactly as they do for an open dialog. It never latches at game over or while Settings or Quit Match? is already open. The latch survives the return: a 'Paused' `ConfirmDialog` (same `rotation` and `progressMessage` lives/score line as Quit Match?) offers Resume, which clears it and restarts the serve pause from scratch, or Quit (`safeBack`, no second confirmation). The hook call and the Paused dialog are the same text in AirHockey, BoxHockey, LightCycles, Pong and Snake.
- **Profile prune:** `useProfiles.tsx` dispatches `@tastic/profile`'s `profileSelectionActions.pruneToRoster(ids)` after both `setAll` calls (the initial reconcile and `onRemoteChange`), so a seat never keeps pointing at a profile a sibling app deleted (its results would land under a ghost id). Unchanged prunes return the same state. Stats of deleted profiles and seat color overrides are deliberately left alone: a transient empty shared-store read would otherwise erase real data. Tested in `useProfiles.test.tsx` against a fake App Group module.
- **Control schemes:** both loadout pickers write through @tastic/input's assignSeatScheme (swap on conflict: picking the other seat's scheme hands it this seat's old one), so the two seats never share a scheme. Without it a 1 Player pick of seat 2's scheme left both seats on it, and KeyboardInputLayer sent every one of those keys to seat 1 in a later 2 Player game.
- **Unreleased packages:** `useBackgroundPause` (planned `@tastic/core` 0.12.0), `pruneToRoster` (`@tastic/profile`, after 0.10.0) and `assignSeatScheme` (`@tastic/input`, after 0.3.0) were installed from local tarballs with `npm install --no-save`. `package.json` ranges still need bumping to the released versions before these changes are committed.

## Achievement toasts (2026-10-14)

`game.tsx` gets every mode's unlocks from `@tastic/achievements` 0.5.0's `broadcastDeviceUnlocks(seats, result.profiles, result.device, profileIds)`: 2 Player passes `[1, 2]`, Vs CPU passes `[1]` and toasts `[1]`. Pong's Solo toasts go through it too, with seat 1's profile. The old Vs CPU merge `[...result.device, ...result.profiles[1]]` toasted a profile's first-round achievements twice (`device` evaluates the whole catalog) and credited a profile with device totals another profile reached; 2 Player broadcast every device unlock onto both seats. Now a seat with a profile gets only `scope: 'device'` entries from `device`, and a guest seat gets all of it. Same change in Snake and LightCycles.

## OS portrait lock (2026-10-08)

The OS is locked to portrait on every device and the app draws all rotation itself (`@tastic/core`'s `OrientationProvider` reads the accelerometer). `@tastic/core`'s Expo config plugin (`"@tastic/core"` in `app.json`'s `plugins`) owns every native setting that depends on: `orientation: "portrait"`; `ios.requireFullScreen` plus a Portrait-only iPad orientation list (audit F009: without it Expo forces all four iPad orientations, so iOS turned the screen on top of the app's own rotation, and Split View, Slide Over and Stage Manager are the price); and `android:appCategory="game"` (Android 16 and later ignore the portrait lock on tablets and unfolded foldables, except for games). Don't set any of those by hand here, and don't add `expo-screen-orientation` (it re-enables upside down on home-button iPhones). The why behind each is in @tastic/core's README. Check the result with `npx expo config --type introspect`; it only takes effect in a new native build.
